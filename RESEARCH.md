# Research notes — AeryxJSON-Parser v1.3.0

Дата обзора: 27 октября 2026 года. Здесь перечислены решения и основания формата; это не утверждение о работоспособности любых ещё не проверенных источников.

## Почему формат изменён

Предыдущая схема была нативным sing-box JSON с одним `selector`. Happ принял такой объект за единый пользовательский профиль `Custom`, а не за список серверов. Это неверно для требуемого интерфейса, где страны должны быть отдельными строками.

В новой реализации `AeryxVPN.json` является **JSON-массивом полных Xray-профилей**. По одному элементу для каждой страны, плюс опциональный общий Auto-профиль. Happ указывает JSON arrays среди поддерживаемых способов подписки, а `remarks` задаёт видимое имя. Поле `meta.serverDescription` предусмотрено для замены технического подзаголовка.

Источники: [Happ JSON docs](https://www.happ.su/main/dev-docs/examples-of-links-and-parameters), [Happ app-management](https://github.com/HappDev/happ_su/blob/main/dev-docs/app-management.md).

## Балансировка внутри профиля

Каждый country-профиль содержит только узлы данной страны. Глобальный Auto содержит все узлы. У каждого профиля есть:

- исходящий канал первого узла с тегом `proxy` — его Happ использует как целевой outbound для сводной информации профиля;
- остальные исходящие каналы с тегами `aeryx-node-NNN`;
- `observatory.subjectSelector` со всеми двумя типами тегов;
- `routing.balancers` с `strategy.type = leastPing`, `fallbackTag = proxy` и селекторами `proxy`, `aeryx-node-`;
- правило маршрутизации для `socks-in`, указывающее на соответствующий балансировщик.

Xray определяет `selector` балансировщика по префиксу тегов. `leastPing` требует данных наблюдателя; без observatory подходящие узлы не получают корректного измерения. Поэтому здесь включены оба компонента. Источники: [Xray routing/balancer](https://xtls.github.io/en/config/routing.html), [Xray observatory](https://xtls.github.io/en/config/observatory.html).

## Преобразование протоколов

Нормализатор текущего парсера используется повторно как промежуточное представление, после чего создаются именно Xray outbounds:

| URI-протокол | Xray outbound | Примечания |
|---|---|---|
| VLESS | `vless` | UUID, flow, TLS/REALITY, WS, gRPC, HTTPUpgrade, XHTTP с проверкой поддерживаемого режима |
| VMess | `vmess` | UUID, alterId/security, TLS и поддерживаемые транспорты |
| Trojan | `trojan` | Пароль и streamSettings |
| Shadowsocks | `shadowsocks` | Метод и пароль; произвольные плагины не переносятся автоматически |
| SOCKS / HTTP(S) | `socks` / `http` | Учётные данные, если они заданы |
| Hysteria2 / HY2 | `hysteria` с `settings.version = 2` | TLS/ALPN и FinalMask salamander при наличии |
| Hysteria v1, TUIC, AnyTLS, SSR | Не публикуются | Нет эквивалентного поддерживаемого Xray outbound в этой схеме; причина отражается в агрегированном отчёте |

Источники: [Xray outbounds](https://xtls.github.io/en/config/outbounds.html), [Xray Hysteria outbound](https://xtls.github.io/en/config/outbounds/hysteria.html), [Xray Hysteria transport](https://xtls.github.io/en/config/transports/hysteria.html).

Неизвестный транспорт не переводится автоматически в TCP. Такая подмена может создать синтаксически допустимую, но неработающую конфигурацию, поэтому режимы, которые нормализатор не может однозначно представить, отклоняются с причиной.

## Геолокация

Сначала используется локальная DB-IP Lite база с адресами, разрешёнными предыдущим этапом. Если база не дала результата, используются существующий флаг/название, затем допустимый код страны в имени хоста. Неопределённые узлы не попадают в случайный регион. Публичная IP-геолокация может отличаться от юридического/физического местоположения сервера; это определяет страну адреса, а не доказывает географическое положение машины.

Источник: [DB-IP Lite](https://db-ip.com/db/download/ip-to-country-lite).

## Валидация и публикация

Workflow загружает официальный стабильный Xray-core, проходит офлайн-тесты, выполняет конвейер разбора и туннельной проверки, генерирует JSON-массив, затем проверяет каждый элемент через `xray run -test -config`. При проверке удаляются только клиентские поля `remarks` и `meta`, после чего Xray валидирует оставшуюся конфигурацию. Данные проверки, содержащие URI, пароли или токены, не выводятся в публичные логи.

Офлайн-тесты подтверждают форму массива, имена, ссылки балансировщика, число узлов и преобразование поддерживаемых URI. Они не доказывают доступность реальных серверов. Только запуск workflow с живыми источниками и туннельной проверкой может подтвердить фактическую работоспособность.

## Ограничение Happ JSON

Happ предупреждает, что Xray JSON-конфигурации передаются Xray напрямую; обычные правила маршрутизации Happ не применяются к JSON-конфигурации автоматически. Поэтому базовая маршрутизация внутри профиля задана явно, а сложные пользовательские правила нельзя считать унаследованными. Источник: [Happ JSON behavior](https://www.happ.su/main/dev-docs/examples-of-links-and-parameters).
